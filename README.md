# Go 服务里 RAG 检索链路的延迟拆解与优化

## 一句话题目

在 Go 后端服务里，把一次 RAG 查询的端到端延迟拆成 embed / retrieve / rerank / generate 四段，
量出每段的占比，逐段优化，在质量不下降的前提下把 P95 延迟降低 50%。

## 为什么做这件事

线上 RAG 接口的 P95 延迟到了 3 秒，用户能明显感觉到卡顿。但没人知道这 3 秒到底花在哪一段，
所有优化都靠猜。我想把这件事变成可测量的——让每一次改动都有前后对比的数字，而不是感觉。

## 我要回答的三个问题

1. 一次 RAG 查询的延迟到底花在哪一段？四段各占多少？
2. 如果只能优化其中一段，优化哪一段性价比最高（每降 100ms 要付出什么代价）？
3. 优化到什么程度会开始伤质量？拐点在哪？

## 这次不做什么（边界）

1. 不做前端和产品化 UI，只做服务端接口 + benchmark
2. 不做模型训练与微调，模型只用现成 API 或本地推理，不碰权重
3. 不做多租户 / 权限 / 计费这些业务功能，成本只在压测里算

## 怎么量

- **数据**：50 条真实 query + 人工标注的期望答案要点（接受不完美）
- **第一指标**：客户端视角的 TTFT（首 token 时间）p50 / p95 / p99
- **分段**：embed / retrieve / rerank / prefill / decode，各段单独记时间戳，全程带 `request_id`
- **注意**：百分位不可相加。各段的 p95 相加不等于整体 p95，必须按 `request_id` 关联 trace 重算
- **成本**：单次 token 数、每 1k query 花费
- **质量**：RAGAS 四件套（context recall / context precision / faithfulness / answer relevance）
- **方法**：每个改动都在同一份数据集上跑前后对比，成功和失败的方案都记录数字

- 一张「延迟 / 成本 / 质量」总数据表
- 3-5 篇带真实数字的公开文章
